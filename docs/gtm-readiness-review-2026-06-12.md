# GTM Readiness Review — 2026-06-12

Multi-agent review (42 agents: 8 domain reviewers, adversarial verification of every critical/high finding, completeness critic) of contracts, compliance, API security, fiat ramps, ops, tests, and product, plus a Stripe subscription revenue scoping. Every finding below was verified against the actual code; critical/high findings were independently re-checked by a second agent attempting to refute them.

## Verdict

**Not GTM-ready.** The architecture is fundamentally sound — non-custodial custody design, correct PII encryption, parameterized SQL, well-built recovery liveness machinery — but there are **4 critical and ~20 verified high-severity issues** across fund safety, PII exposure, and a money-in flow that does not work in the launch geography. Realistic path to a CEMAC public launch: **3 phases, roughly 6–8 focused weeks**, detailed at the end of this document.

## The Four Criticals

1. **Escrow funds can be permanently locked** (`move/sources/njangi_cycle_escrow.move`) — the canonical per-cycle escrow (the path the UI uses) has no refund, cancel, or timeout path. One member dropout, a lost recipient, or a duplicate `open_cycle` strands the entire cycle pot forever. Escrow balances are also entirely outside the member-initiated recovery flow. Only rescue today: emergency package upgrade.
2. **Real user PII is committed to git history** (`salt-database.db`, `src/services/combined.log`, `error.log`, `dump.rdb`) — real Google OAuth `sub` identifiers, encrypted zkLogin salts, and recovery-code hashes. Requires history scrub (filter-repo/BFG), key rotation, and treating affected users as a PII exposure.
3. **Anonymous PII decryption endpoint** (`src/pages/api/whatsapp/admin-link-circle.ts:67-150`) — `GET ?circleId=<public>&includeRecipient=true` decrypts and returns the linked WhatsApp phone number for any circle to any caller, defeating the entire Walrus encryption design.
4. **WhatsApp webhook accepts forged signatures by design** (`src/pages/api/whatsapp/webhook.ts:247-263`) — a "TEMPORARY: allow invalid signatures for debugging" bypass ships in production; attackers can drive the bot and send WhatsApp messages from the business number.

## Top verified highs (by domain)

- **Contracts:** legacy payout over-pays by one contribution per cycle, silently draining commingled security deposits (`njangi_payments.move:393,442`); legacy contribute paths let one member satisfy "all contributed" by paying multiple times; the escrow money path and the `advance_circle_after_claim` rotation fix have **zero tests** (and the Move test suite currently does not even compile under the toolchain).
- **Compliance:** the KYC gate lives in browser localStorage and cycle-opening is permissionless — it is advisory, not enforced; ramp webhooks mint on-chain attestations claiming sanctions/jurisdiction screening **that was never performed**; revocation breaks permanently if the AttestorCap moves to a multisig (revoke is bound to the original issuer address).
- **Money-in:** the geo-aware RampPicker is dead code — every live flow hardcodes Coinbase + `country="US"`, so **a CEMAC user cannot fund a wallet in-app at all**; the Transak webhook fails open when its secret is unset; the Coinbase webhook verifies a re-serialized body (legit webhooks will fail signature checks).
- **Ops:** the on-chain mainnet package is a stale v1 missing every module the current app calls; the cycle-finalized notifier never sends the recipient (every "your turn" nudge silently no-ops) and its cursor logic is inverted; ~179 files of uncommitted work on main **including the deployed contract sources**; zkLogin sessions (with ephemeral private keys) live in one process's memory; no health endpoint, error tracking, or alerting anywhere.
- **Auth:** salt issuance decodes JWTs without verifying signatures (`api/salt.ts`, `persistent-salt-service.ts`); the admin-auth middleware accepts any non-empty token and is wired to zero routes.
- **Product/legal:** ToS + privacy policy exist as orphaned HTML files in `public/` (dated Jan 2025, still referencing the retired yield feature) — linked nowhere, no acceptance gate; French i18n covers only the escrow panel in a majority-francophone market; README still describes the pre-redesign custodial model.
- **Missed by the main review, caught by the critic:** Walrus PII blobs expire after 5 epochs with no renewal (every WhatsApp link dies on a timer while its on-chain anchor lives forever); business-initiated WhatsApp messages use freeform text, which Meta rejects outside the 24-hour window — **even after fixing the notifier bugs, nothing would deliver**; no gas sponsorship exists despite CLAUDE.md advertising it (users must self-fund gas — fatal for CEMAC onboarding).

## Launch sequence (recommended)

**Phase A — Fund safety + PII (the "do not pass go" set, ~2-3 wks)**
1. Escrow refund paths: `cancel_unfinalized_after_deadline` + expired-claim refund; wire escrow into recovery or disclose its absence. Fix/retire the legacy payout overpay + contribute dedup. Fix the Sui test toolchain; add escrow + `advance_circle_after_claim` lifecycle tests. Republish testnet; commit the working tree.
2. Git history scrub + key rotation. Auth on the PII-decrypt GET. Remove the webhook signature bypass. JWKS verification on salt issuance. Real admin auth on link/unlink routes.

**Phase B — Money-in + compliance honesty + legal (~2 wks)**
3. Wire RampPicker for real; enable an XAF-capable ramp (Transak) end-to-end; fix Transak fail-open + Coinbase raw-body. Stop logging ramp PII.
4. Attestations must claim only what the partner attested; move the KYC-required flag on-chain; fix AttestorCap revocation coupling.
5. ToS/privacy/risk-disclosure pages (EN+FR) with acceptance gating signup; fix data-deletion flow.
6. WhatsApp: approved message templates (Meta policy), Walrus blob renewal job, fix notifier recipient + cursor.

**Phase C — Production hardening + GTM polish (~2-3 wks)**
7. Mainnet publish + bootstrap; Postgres-backed sessions; health endpoint + Sentry + worker heartbeat; release-phase migrations; deploy or fold in whatsapp-bot-backend; gas sponsorship via Enoki (or fund-first-tx onboarding).
8. French for the core funnel; README rewrite; support channel; PWA service worker.
9. Stripe subscription build (see appendix) — can proceed in parallel with Phase C since it touches the SaaS layer only.

# Detailed findings by domain
## Move Smart Contracts

The Move layer is broadly well-structured for a non-custodial ROSCA: custody's public withdraw levers were removed, fund movers are package-internal, the asset registry uses exact-type matching, PII is off-chain (Walrus pointers only), and the member-initiated recovery/liveness machinery is thoughtfully built and well unit-tested at the helper level. However, the canonical per-cycle escrow path (the one the UI now uses, njangi_cycle_escrow) has a serious gap: contributed funds have NO refund, cancel, or recovery path and sit entirely outside the member-initiated recovery flow, so they can be permanently locked. Separately, the legacy custody contribution/payout path remains fully published and callable, and it both over-pays (contribution x member_count vs the contribution x (member_count-1) actually collected) and lacks per-member per-cycle contribution de-duplication, allowing security deposits to be drained. The canonical escrow fund flow and the previously-buggy advance_circle_after_claim fix have zero unit tests.

### Launch blockers
- Add a refund/recovery path for per-cycle escrow funds (cancel-unfinalized-after-deadline and expired-claim refund), or wire escrow balances into execute_recovery. As built, an unresponsive recipient, a dropped member, or a duplicate/mis-parameterized escrow permanently locks an entire cycle pot with no recovery — and the canonical escrow flow is not covered by the advertised member-initiated recovery at all.
- Fix or remove the legacy custody payout path: trigger_automatic_payout pays contribution x member_count while only contribution x (member_count-1) is collected, draining commingled security deposits; and contribute/contribute_stablecoin allow one member to satisfy has_all_members_contributed by paying multiple times. Both are publicly callable on-chain today (contribute_stablecoin is wired into the live UI).
- Add integration tests for the escrow money paths (contribute/finalize/redeem) and especially advance_circle_after_claim (the rotation-advance fix) before publishing; today they have zero coverage.
- Reconcile the published code with the 'no admin discretionary fund movement' claim by removing/constraining process_scheduled_payout and process_security_deposit_return.

### Verified findings (critical/high — each adversarially re-checked)
#### [CRITICAL] Per-cycle escrow has no refund/recovery path — funds permanently lockable, and entirely outside member-initiated recovery
`move/sources/njangi_cycle_escrow.move:73-96,278-337,385-413,472-488`

CycleEscrow<T> holds member contributions in its own Balance<T>. The only way funds ever leave is redeem_claim, which requires (a) the escrow reached required_contributors and was finalized, and (b) the predetermined recipient calling within CLAIM_WINDOW_MS = 30 days (line 60, enforced at line 398). There is NO cancel, refund, withdraw-my-contribution, or timeout-sweep function anywhere in the module (verified by grep: no refund/cancel/withdraw symbols). Consequences: (1) If a cycle never reaches required_contributors (a member drops out, or open_cycle is called twice and contributions split across duplicate escrows), every contributor's funds are stuck forever. (2) If the recipient is lost/unresponsive, the circle cannot advance (advance_circle_after_claim asserts escrow.claimed at line 479, and only the recipient can redeem), and after 30 days redeem_claim aborts E_CLAIM_EXPIRED leaving the whole pot locked with finalized=true blocking any re-mint. (3) The advertised member-initiated recovery (njangi_circles::execute_recovery / trigger_auto_release) only refunds the CustodyWallet and member recovery balances — it never touches CycleEscrow objects — so for the canonical escrow flow, recovery cannot return contributed funds at all.

**Fix:** Add a permissionless refund path to the escrow: e.g. a contribution-refund window or an admin-less 'cancel_unfinalized_after_deadline' that returns each table-recorded contributor their exact contribution if the cycle is not finalized by snapshot.due_at_ms + grace, plus an 'expired_claim_refund' that splits escrow.balance back to contributors once a finalized claim passes its expiry unredeemed. Wire escrow balances into execute_recovery, or document explicitly that escrow circles have no recovery and gate them behind that disclosure before launch.

*Verification:* Verified: njangi_cycle_escrow.move's only fund-exit is redeem_claim (balance::split at line 404), gated on finalization (line 532 requires required_contributors) and a 30-day recipient-only claim window (lines 60, 394, 398) with finalized=true (lines 531/533) blocking re-mint after expiry — no refund/cancel/timeout function exists and CycleEscrow is referenced in no other module. Recovery (njangi_circles.move:2639-2670) only refunds CustodyWallet balances and never touches CycleEscrow, so a single member dropout or a lost recipient permanently strands the entire pot of the canonical escrow flow; the only rescue is a centralized emergency package upgrade via the retained UpgradeCap.

#### [HIGH] Legacy rotational payout over-pays by one contribution per cycle, draining commingled security deposits
`move/sources/njangi_payments.move:393,442,486`

trigger_automatic_payout computes the rotational payout as contribution x member_count (stablecoin path line 393: safe_mul(stablecoin_per_member, member_count); SUI path line 442: safe_mul(contribution_amount_raw, member_count)). But the cycle only collects contribution x (member_count - 1): has_all_members_contributed (njangi_circles.move:3047) excludes the recipient via expected_cycle_contributions_usd (njangi_circles.move:3290-3306, contributing_members = active_members - 1). The escrow path agrees with that economics (required_contributors = member_count - 1, Claim amount = full balance). So the legacy path pays out one extra contribution every cycle. Because legacy contributions and security deposits commingle in the same CustodyWallet Balance/dynamic field (deposit_contribution_coin and internal_store_security_deposit both call store_coin_balance), the shortfall is silently drawn from members' security deposits, and later cycles eventually abort EInsufficientTreasuryBalance — leaving the final recipients unpayable and deposits unreturnable. trigger_payout is public/permissionless, so this is reachable on any active circle.

**Fix:** Make the legacy payout amount contribution x (member_count - 1) to match what is collected and what the escrow pays, or formally retire/remove trigger_payout + trigger_automatic_payout from the published package now that the escrow path is canonical. At minimum, never let a payout draw from the deposits portion of the custody balance.

#### [HIGH] Legacy contribute paths lack per-member per-cycle de-duplication, letting one member unlock payout and over-withdraw
`move/sources/njangi_payments.move:203-254; move/sources/njangi_circles.move:1941-2009`

Neither njangi_payments::contribute (SUI) nor njangi_circles::contribute_stablecoin checks whether the sender already contributed for the current cycle. Both unconditionally increment circle.contributions_this_cycle (payments line 241; circles line 1992). has_all_members_contributed (njangi_circles.move:3094) only compares the aggregate USD-cent counter to expected, never tracking distinct contributors. (The escrow path is immune: njangi_cycle_escrow.move:317 asserts !table::contains(contributed, sender).)

**Fix:** Track a per-member 'contributed_this_cycle' flag (like the escrow's contributed table) in the legacy contribute paths and reject duplicates, or retire the legacy custody contribution path entirely in favor of the escrow flow before GTM.

*Verification:* Confirmed: njangi_payments::contribute (203-254) and njangi_circles::contribute_stablecoin (1941-2009) have no per-member per-cycle dedup or recipient-exclusion and both unconditionally call add_to_contributions_this_cycle (payments:241, circles:1992); has_all_members_contributed (3047) only compares the aggregate counter against contribution*contributing_members (3094, 3290), so one member can self-fund the gate and trigger_payout (848) pays member_count*contribution from the commingled wallet that includes security deposits — exactly the attack the immune escrow path guards against (njangi_cycle_escrow.move:316-317). ## Compliance Layer

The compliance layer is a well-architected PII-minimizing attestation anchor (opaque SHA-256 policy hash + HMAC ref hash, client-side signing, AttestorCap-gated issuance, non-transferable on-chain attestations) with real Move-level enforcement for gated escrows. However, the gate is not authoritative: whether a circle requires KYC lives only in the admin's browser localStorage, opening a cycle is permissionless, and there is no on-chain circle-level "requires attestation" flag, so the KYC gate is trivially bypassable by anyone hand-rolling the ungated open_cycle/contribute path. Separately, the ramp webhooks convert a completed fiat *purchase* into an on-chain attestation that asserts "sanctions screened, jurisdiction allow-listed" — checks Njangi never performs or evidences — creating a misrepresentation/liability exposure. The known deferred items (sanctions screening, jurisdiction blocking, travel rule, AML monitoring, mandatory gate, ToS/risk disclosures) are confirmed absent in code; for a CEMAC pilot most are deferrable, but the over-attestation, the missing ToS/risk-disclosure acceptance gate, and a revocation-coupling bug are launch-blocking regardless of market.

### Launch blockers
- Stop minting attestations that assert 'sanctions screened, jurisdiction allow-listed' on a completed fiat purchase (ramp-kyc-bridge.ts:88-91; coinbase/moonpay webhooks). Either gate issuance on a real KYC-completion event and set criteria to exactly what the partner attested, or remove the false claims — anchoring unperformed compliance checks on chain is a misrepresentation/liability risk in any market.
- Do not represent the KYC gate as enforced. Today it is opt-in via browser localStorage and bypassable because cycle-opening is permissionless and there is no on-chain circle-level requirement. Before claiming KYC enforcement to partners/regulators/users, move the requirement on-chain and force the gated open path for required circles.
- Add a versioned Terms of Service + risk-disclosure acceptance gate (smart-contract risk, irreversibility, wallet loss, no deposit insurance, sanctions/PEP exclusions) recorded with consent, before first contribute/collect — required even for a CEMAC consumer pilot.
- Fix the revocation/issuer-address coupling (njangi_compliance.move:152-170) so the operator can always revoke previously-issued attestations after moving the AttestorCap to a multisig; otherwise the primary safety control can be silently disabled.
- Confirm production operational prerequisites: DATABASE_URL set (queue persistence), AttestorCap held in a multisig with issuance/revocation always signed from that same address, and COMPLIANCE_ISSUANCE_SECRET separated from INTERNAL_NOTIFY_SECRET.

#### [HIGH] KYC compliance gate is non-authoritative and bypassable (per-circle requirement lives in browser localStorage; opening a cycle is permissionless)
`src/pages/circle/[id]/manage/index.tsx:717-720,852-860,7537-7559 + move/sources/njangi_cycle_escrow.move:150-200`

## Fiat Ramps & Money-In

The fiat-ramp money-in stack is well-structured on the Coinbase session side (zod validation, dual rate limits, CORS, server-only signing keys) but has launch-blocking defects in webhook authentication and geo-routing. Two webhook verifiers are effectively broken or fail-open (Transak accepts forged events when its secret is unset; Coinbase verifies a re-serialized body that will not match the provider's raw-byte signature), and customer PII is written to logs. Critically for a Cameroon/CEMAC launch, the geo-aware RampPicker is dead code and every live flow hard-codes Coinbase with country="US" while MoonPay/Transak ship disabled — so money-in is essentially unusable in the launch geography. The riskiest swap code is behind an off-by-default flag and protected by on-chain minAmountOut, lowering its launch exposure.

### Launch blockers
- Close the Transak webhook fail-open (src/services/transak-service.ts:74-80): never accept events when TRANSAK_API_SECRET is unset, and gate the Transak 'enabled' flag on the secret being present. As-is, enabling Transak lets anyone forge KYC/compliance attestations and spam members.
- Fix Coinbase webhook signature verification to operate on the raw request bytes (bodyParser:false + raw stream), otherwise legitimate Coinbase KYC webhooks are rejected and the attestation/WhatsApp confirmation flow silently never fires.
- Make money-in actually work for the launch geography: enable and wire MoonPay/Transak with geo-aware ordering (RampPicker is currently dead code) and pass the real country instead of the hardcoded 'US'. Today every CEMAC/Cameroon user hits Coinbase UNSUPPORTED_REGION with no enabled fallback.
- Stop logging unredacted customer PII (email, name, phone) in onramp webhook persistence (src/lib/onramp-logging.ts) before processing real KYC traffic.

## Operations & Deployment

Operationally this repo is a well-run testnet pilot with real deploy discipline (env validation, idempotent migrations/bootstrap, manifest-drift CI guards, a smoke gate) — but it is not mainnet-deployable today. The two hard blockers are that the on-chain mainnet package is a stale v1 publish missing every module the current app calls (verified against the mainnet fullnode), and that a real user salt database plus runtime logs are committed to the public git history. Beyond those, the launch-week embarrassments are concentrated in the worker/bot tier: the WhatsApp 'your turn' notifier silently notifies nobody (recipient never sent, cursor logic inverted), the bot backend is unreproducible and unreachable in the Procfile layout, and there is zero monitoring — no health endpoint, no error tracking, no alerting. #### [HIGH] Notifier event pagination is inverted: queries ascending but persists the oldest event id as the cursor

## Web/API Security

The codebase has solid building blocks (correct AES-256-GCM PII encryption, parameterized SQL everywhere, properly-verified Coinbase/MoonPay webhook signatures, centrally-guarded compliance endpoints), but several launch-blocking gaps undercut them. Real user PII (OAuth subject IDs) is committed to git, the WhatsApp PII-decryption endpoint is reachable with no authentication, and the WhatsApp webhook deliberately accepts forged signatures. The 'admin auth' middleware is a non-functional stub that is never wired to any route, so admin endpoints have no server-side authorization at all.

### Launch blockers
- Scrub salt-database.db, salt-database.json, src/services/combined.log, src/services/error.log and dump.rdb from git history and rotate the salt-service encryption key (real OAuth subject PII is in the repo).
- Add authentication/authorization to the WhatsApp admin-link-circle GET so it cannot decrypt and return members' phone numbers to anonymous callers.
- Enforce WhatsApp webhook HMAC signature verification (remove the 'allow invalid signatures for debugging' bypass).
- Replace the stub admin-auth middleware with real verification (or gate the admin link/unlink endpoints explicitly) so PII/Walrus/index side effects require a verified circle admin.
- Verify OAuth JWT signatures (JWKS) before issuing or recovering zkLogin salts in api/salt.ts and persistent-salt-service.ts.

### Verified findings (critical/high — each adversarially re-checked)
#### [CRITICAL] Real user PII committed to git (OAuth sub IDs, zkLogin salts, recovery hashes, server logs)
`salt-database.db (repo root, tracked); src/services/combined.log`

git ls-files shows salt-database.db, salt-database.json, src/services/combined.log, src/services/dump.rdb, and src/services/error.log are tracked. salt-database.db contains 3 real records: Google sub identifiers, aud (Google OAuth client IDs), AES-encrypted zkLogin salts, and SHA-256 recovery-code hashes. combined.log (27KB) logs the same real sub/aud/iss in plaintext. The AES key (.encryption-key) is NOT committed, so the salts themselves aren't directly recoverable, but the OAuth subject identifiers are plaintext PII (GDPR online identifiers) that deanonymize users and are bound to the zkLogin address-derivation scheme. *.db is in .gitignore now, but these files were committed before the rule and remain in history.

**Fix:** Purge these blobs from the full git history (git filter-repo/BFG), force-push, rotate the salt-service encryption key and any leaked OAuth client secret, and add salt-database.json + src/services/*.log + *.rdb to .gitignore. Treat the 3 affected users as a PII exposure.

#### [CRITICAL] Unauthenticated endpoint decrypts and returns members' WhatsApp phone numbers
`src/pages/api/whatsapp/admin-link-circle.ts:67-150`

handleGet has no authentication. With ?circleId=<public id>&includeRecipient=true it loads the on-chain link, calls fetchAndDecryptPII(walrusBlobId), and returns recipient (the plaintext phone_e164 / group_id) in the JSON response (lines 131-149). circleIds are public on-chain and appear in app URLs. This lets any anonymous caller retrieve the linked WhatsApp phone number for any circle, completely defeating the Walrus encryption design. The legitimate frontend (WhatsAppCircleIntegration.tsx:137) does not even pass includeRecipient, so this is purely an exposed capability.

**Fix:** Require proof of circle admin (signed challenge / verified zkLogin session matching the on-chain admin) before decrypting. At minimum gate the includeRecipient path behind server-side auth; never return decrypted PII to an unauthenticated GET.

#### [HIGH] WhatsApp webhook accepts forged/invalid signatures
`src/pages/api/whatsapp/webhook.ts:247-263`

After computing the HMAC and calling timingSafeEqual, an invalid signature only logs 'Invalid webhook signature - allowing anyway for debugging' and falls through to full message processing. The catch handler at 257-263 likewise 'allows anyway' on any verification error (timingSafeEqual throws on length mismatch). Net effect: signature verification is non-enforcing. An attacker can POST forged Meta webhook payloads to drive the bot — sending arbitrary WhatsApp messages from the business number to attacker-chosen recipients (msg.from is attacker-controlled) and querying circle status.

**Fix:** Return 403 on signature mismatch or verification error; remove the debug bypass. Also require the signature+secret to be present (currently if either is missing, verification is skipped entirely).

#### [HIGH] Admin auth middleware is a stub and is not applied to any route
`src/middleware/admin-auth.middleware.ts:92-111`

verifyAdminToken returns a valid admin object for ANY non-empty string — comment says 'placeholder implementation'. More importantly, grep confirms withAdminAuth/requireAdminAuth/verifyAdminToken are never imported by any route; only logAdminAction (a logger) is used. So admin-link-circle.ts:176 and admin-unlink-circle.ts:41 read adminAddress straight from the request body with no verification. The on-chain Move call may enforce admin for the anchoring tx, but the PII-encrypt + Walrus upload + Postgres phone-index side effects (admin-link-circle.ts:224-288) run before any chain check and with no auth, so an anonymous caller can write arbitrary encrypted blobs to Walrus and pollute the phone-to-circle index.

**Fix:** Either implement real token verification (verify the zkLogin session / signed message and confirm the address is the on-chain circle admin) and wire withAdminAuth onto the admin routes, or delete the misleading middleware and gate these endpoints explicitly. Do not perform side effects before authorization.

#### [HIGH] Salt issuance does not verify the OAuth JWT signature
`src/pages/api/salt.ts:24; src/services/persistent-salt-service.ts:210,276`

Both salt services call jose decodeJwt(token) (decode only, no signature/issuer verification) and derive sub/aud from it. Anyone can craft an unsigned JWT with an arbitrary sub/aud and obtain or seed a salt for that identity. zkLogin requires the salt to be confidential and issued only to the authenticated user; an attacker can use this to deanonymize a victim's Sui address or, for the in-memory local-salt-service, poison the salt for a sub before the real user's first login. persistent-salt-service recover-salt (276) has the same flaw plus relies only on the recovery code.

**Fix:** Verify the JWT against the provider JWKS (jwtVerify with issuer/audience checks) before issuing or recovering any salt.

## What the Review Itself Missed (Completeness Critic)

## Appendix: Stripe Subscription Scoping (raw)

### User identity model
Identity is zkLogin-derived and address-centric; there is NO users table. Flow: OAuth JWT -> (sub, aud) -> per-user salt -> deterministic Sui address via jwtToAddress(jwt, userSalt) (src/services/enokiZkLoginService.ts:389-400 generateUserAddress; callback processing at :458-495 requires jwtPayload.sub/aud, fetches salt, derives userAddr). The AccountData object (src/services/zkLoginService.ts:33-44) carries provider, userAddr, sub, aud, userSalt, ephemeralPrivateKey, zkProofs, maxEpoch, name, picture — persisted client-side only in localStorage (src/contexts/AuthContext.tsx:127-191, 242-244). The ONLY durable server-side per-user record is the Postgres `salts` table keyed UNIQUE(sub, aud) (scripts/migrate-postgres.mjs:47-57; src/services/postgres-adapter.ts:87-109), plus `recovery_codes` FK'ing salts.id. Everywhere else (join_requests.user_address, whatsapp_notifications.target_address, compliance attestations) the Sui address IS the identity. Email exists in the JWT but is only used as a display-name fallback (enokiZkLoginService.ts:508-513); the `mainnet_signups` table (migrate-postgres.mjs:90-102) stores email but is a marketing waitlist, not auth-bound. RECOMMENDED Stripe customer key: the Sui address (userAddr) as the primary lookup + (sub, aud) stored alongside as the root identity anchor, with all three written into Stripe customer metadata. Rationale: address is what every feature/gate already keys off; (sub, aud) is collision-safe across providers (aud is the per-provider OAuth client id) and survives even if the salt DB is the only thing left. CAVEAT: same human logging in via a different provider gets a different aud -> different salt -> different address, so one person can hold multiple entitlement identities; also note iss is never persisted. Server-side session validation exists only inside /api/zkLogin (in-memory `sessions` Map + cookie, src/pages/api/zkLogin.ts:1088-1125) — other API routes like join-requests/create.ts trust a client-supplied userAddress with no auth, so Stripe checkout endpoints will need a real server-verified binding of session -> sub/aud/address before issuing entitlements.

### Risks
- Regulatory perception: the product's legal posture rests on being a non-custodial coordinator (CLAUDE.md: 'Njangi never settles fiat directly', no admin discretionary fund movement). A flat SaaS subscription for software features is the safest monetization (no per-transaction fee on fund flows, which would look like compensation for money transmission). Do NOT gate contribute/claim/payout/recovery actions behind payment — charging to access one's own escrowed funds would directly undermine the non-custodial/MSB-exempt argument and is reputationally toxic. Gate coordination conveniences (WhatsApp, analytics, circle size) only.
- Stripe acceptability risk: Stripe's restricted-business policy treats crypto-adjacent and rotating-savings/financial-club businesses with heightened scrutiny; a ROSCA coordinator on Sui may require Stripe pre-approval or get classified as high-risk. Validate with Stripe before building (memory file 'compliance gaps deferred' already lists sanctions screening/jurisdiction blocking as unfinished — Stripe onboarding will surface these).
- Market-fit risk on payment rails: the target user base (CEMAC-region njangi participants) onboards via fiat ramps precisely because conventional card rails are weak there; Stripe card-subscription conversion may be structurally limited in primary markets. Consider Stripe for diaspora admins (likely the payer persona) and keep the payer = circle admin, not every member.
- Architectural bypassability: all Move entry points are permissionless by design (trigger_payout, create_circle, set_max_members) and the Phase 2 client-side signer (src/lib/zklogin-client-signer.ts) signs in-browser and submits directly to RPC, bypassing /api/zkLogin entirely. Any on-chain feature gated only in the API/UI is advisory. Genuinely enforceable gates are limited to server-mediated services: WhatsApp notifications/linking (Walrus PII encryption happens server-side with WALRUS_PII_MASTER_KEY), join-request DB workflow, and server-computed analytics. Price the product around those.
- State-durability risk: /api/zkLogin sessions live in an in-memory Map, the rate limiter (src/lib/rate-limit.ts) and Coinbase webhook dedupe (coinbase/webhook.ts:45-46) are per-instance in-memory. Reusing these patterns verbatim for Stripe risks double-provisioning entitlements on webhook retries and broken auth behind a load balancer; billing needs DB-backed sessions and durable event idempotency.
- Raw-body signature pitfall: the Coinbase webhook verifies HMAC over JSON.stringify(req.body) (coinbase/webhook.ts:97-105) because bodyParser stays enabled — copying this for Stripe will cause intermittent signature failures; must use the MoonPay bodyParser:false pattern (moonpay/webhook.ts:18).
- Identity fragility for entitlements: Stripe customer keyed to a Sui address breaks if the user logs in with a different OAuth provider (different aud -> different salt in the salts table keyed UNIQUE(sub,aud), migrate-postgres.mjs:47-57 -> different address). One human can hold multiple addresses; store (sub, aud) + address and plan an account-linking story before launch, or entitlements will appear to 'vanish' on provider switch.
- PII scope creep: the architecture deliberately keeps PII off servers (AES-256-GCM Walrus blobs, hashed phone index). Stripe introduces names, emails, and billing addresses into scope via Stripe-hosted records and webhook payloads — privacy policy, data-flow documentation, and the Walrus-centric privacy claims need updating before charging users.
