# Legal Acceptance Gate — Implementation Spec

> Status: draft spec for the engineer wiring the gate. The legal documents in this
> directory are **DRAFT — requires review by qualified counsel before publication.**
> Do not ship the gate pointing at unapproved document versions.

## Goal

Record verifiable, versioned user acceptance of three documents — Terms of Service,
Privacy Policy, and Risk Disclosure (EN + FR, sources in `docs/legal-drafts/`) — before a
user can use the product, and re-prompt on any version bump. The GTM review
(`docs/gtm-readiness-review-2026-06-12.md`, "No Terms of Service / risk-disclosure
acceptance gate") flags this as launch-blocking.

## Documents and versioning

- Canonical doc ids: `terms`, `privacy`, `risk`. Version = the `version` field in each
  file's front-matter (semver string, starts at `1.0.0`). EN and FR are the same legal
  document; acceptance is per doc id + version, with the locale the user read recorded
  for evidence.
- Publish rendered copies at `/legal/terms`, `/legal/privacy`, `/legal/risk` (with `?lang=en|fr`),
  replacing the orphaned, stale Jan-2025 HTML files in `public/` (do **not** reuse their
  yield-era content). Keep prior versions reachable (e.g. `/legal/terms?version=1.0.0`).
- Expose current versions to the client from a single constant, e.g.
  `src/lib/legal-docs.ts`: `{ terms: '1.0.0', privacy: '1.0.0', risk: '1.0.0' }`. Bumping a
  constant + adding the new markdown is the whole release procedure for a new version.

## Storage: `legal_acceptances` (Postgres)

Add to the `STATEMENTS` array in `scripts/migrate-postgres.mjs`, following its
conventions (idempotent `CREATE TABLE IF NOT EXISTS`, TEXT identifiers, TIMESTAMPTZ):

```sql
CREATE TABLE IF NOT EXISTS legal_acceptances (
  id            BIGSERIAL PRIMARY KEY,
  sub           TEXT NOT NULL,            -- OAuth subject (root identity, same as salts table)
  aud           TEXT NOT NULL,            -- OAuth client id (provider-scoped)
  user_address  TEXT NOT NULL,            -- derived Sui address at time of acceptance
  doc           TEXT NOT NULL CHECK (doc IN ('terms','privacy','risk')),
  version       TEXT NOT NULL,            -- semver from doc front-matter
  locale        TEXT NOT NULL DEFAULT 'en' CHECK (locale IN ('en','fr')),
  accepted_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  ip_hash       TEXT                      -- HMAC-SHA256(ip, LEGAL_ACCEPT_IP_SALT), never the raw IP
);
CREATE UNIQUE INDEX IF NOT EXISTS legal_acceptances_unique
  ON legal_acceptances (sub, aud, doc, version);
CREATE INDEX IF NOT EXISTS legal_acceptances_address_idx
  ON legal_acceptances (user_address);
```

Notes:

- Key on `(sub, aud)` — the only durable server-side identity (same key as the `salts`
  table). `user_address` is stored alongside for audit/joins, not as the key, because one
  human can hold multiple addresses across providers.
- `ip_hash`: HMAC with a dedicated server-side salt (`LEGAL_ACCEPT_IP_SALT`, generated by
  `npm run generate:secrets`; add to `scripts/validate-env.mjs`). Never store raw IPs —
  consistent with the phone-number HMAC index pattern in `whatsapp-link-index`.
- Rows are **append-only** (re-acceptance of a new version inserts a new row). Never
  update or delete; on a user PII-deletion request these rows are *retained* as
  consent/defense-of-claims records — the privacy policy's retention section says so.

## API

Two endpoints under `src/pages/api/legal/`:

1. `GET /api/legal/status` — input: authenticated identity (see Auth below). Output:
   `{ required: [{doc, currentVersion, acceptedVersion|null}], allAccepted: boolean }`.
   Compares the user's latest accepted version per doc against `legal-docs.ts`.
2. `POST /api/legal/accept` — body: `{ docs: ['terms','privacy','risk'], locale }`.
   Server resolves versions itself from `legal-docs.ts` (never trust client-supplied
   versions), computes `ip_hash` from the request IP, inserts one row per doc
   (`ON CONFLICT DO NOTHING` against the unique index for idempotency). Reject unless
   *all three* docs are being accepted on first signup.

Auth: do **not** follow the `join-requests/create.ts` pattern of trusting a client-supplied
address. Bind acceptance to the verified zkLogin session: reuse/extend the session
validation in `/api/zkLogin` (per the GTM review's Stripe scoping, step 1 of its
integration plan — a server-verified `{sub, aud, userAddr}` primitive). The Stripe billing
track needs the same primitive; coordinate so both use one helper. Apply the in-process
rate limiter (`src/lib/rate-limit.ts`) to both endpoints.

## When the gate triggers

1. **First zkLogin signup** — after OAuth callback completes and the address is derived,
   but **before** the user reaches the dashboard or any server-mediated action. Hook into
   the post-auth flow in `src/contexts/AuthContext.tsx`: after account data is set, call
   `GET /api/legal/status`; if `!allAccepted`, render the blocking modal.
2. **Any version bump** — same status check runs on every session restore/login. If any
   doc's `acceptedVersion` ≠ `currentVersion` (including null), the modal reopens showing
   only the changed doc(s), with a short "what changed" line. Per the ToS, material
   changes also get ≥30 days' in-app/email notice before the version flips.
3. **Server-side enforcement** — UI gating alone is insufficient. Add an
   `assertLegalAccepted(sub, aud)` guard (clone the `src/lib/compliance-gate.ts`
   architecture: feature flag `NEXT_PUBLIC_LEGAL_GATE_ENABLED`, typed error code) and wire
   it into server-mediated endpoints: the `/api/zkLogin` `sendTransaction` broker,
   `join-requests/create`, WhatsApp link routes, and (when built) billing checkout.
   Honest limitation: users signing client-side and submitting directly to Sui RPC bypass
   any server gate — the gate's purpose is recorded consent and interface gating, not
   on-chain enforcement. **Never** gate claim/recovery reads or recovery execution paths
   on acceptance status (mirror of the "recovery is never paywalled" rule).

## UX

- **Blocking modal** (no dismiss/escape; covers the app shell) titled "Before you start"
  / « Avant de commencer ».
- **FR/EN toggle** top-right, defaulting from the existing locale state
  (`src/lib/i18n.ts` / `LocaleSwitcher`); toggling re-renders all three doc summaries and
  the checkbox labels. Record the locale active at the moment of acceptance.
- **Risk disclosure is displayed inline and scrollable** (it is short by design,
  `risk-disclosure.{en,fr}.md`). The risk checkbox stays disabled until the user has
  scrolled to the bottom (`IntersectionObserver` on an end-of-document sentinel).
- **Terms and Privacy** render as titled rows with a one-line summary and a "Read" link
  opening the full doc (new tab or in-modal viewer). No scroll requirement for these two.
- **One explicit checkbox per document** (3 total), unchecked by default, each naming the
  doc and version, e.g. "I have read and accept the Terms of Service (v1.0.0)". No
  master "accept all" checkbox.
- Continue button enables only when all three boxes are checked; on click POST
  `/api/legal/accept`, show a spinner, and only proceed on 2xx (retry UI on failure —
  never proceed optimistically).
- On version-bump re-prompt, show only the changed doc(s) with their new versions.
- Accessibility: focus-trap the modal, `aria-modal`, keyboard-checkable boxes — the GTM
  review flags accessibility as untouched; don't make the first legally significant
  interaction the worst one.

## Out of scope (explicitly)

- Email capture form consent (the landing waitlist) — needs a simple privacy-notice
  checkbox too, but is a separate, lighter change.
- On-chain anchoring of acceptance hashes — not required; Postgres records suffice.
- pcm/sw/am/ar/fa translations — EN/FR only at launch, matching the legal drafts.

## Test checklist

- Migration is idempotent (run `npm run migrate:postgres` twice).
- First-login user is blocked everywhere until acceptance; rows written with correct
  `sub/aud/address/doc/version/locale/ip_hash`.
- Duplicate POST is a no-op (unique index), returns success.
- Version bump of one doc re-prompts for that doc only; old rows preserved.
- `POST /api/legal/accept` without a valid session is rejected (401), as is a body
  attempting to set versions.
- Risk checkbox cannot be checked before scroll-to-bottom; FR toggle persists to the
  recorded row.
- Recovery/claim flows remain reachable for a user who has NOT accepted the new version
  (read-only legal hold must never lock funds access).
