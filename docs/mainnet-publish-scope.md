# Mainnet Contract Publish — Scoping & Runbook

_Generated 2026-06-14 from a 4-investigator read-only audit of the live repo + mainnet chain state. Verdict and corrections cross-checked against current `move/sources/`._

## Verdict

NO-GO for a mainnet publish TODAY (2026-06-14). A FRESH publish is technically MANDATORY and the mechanics are sound — but the launch posture is not ready. Note: I verified against the actual repo and three of the four "fund-safety criticals" the cost-risk investigator cited are STALE and already fixed in the current code (the same code targeted for mainnet); the remaining blockers are governance/audit/launch-readiness, not fund-logic bugs.

WHAT IS ACTUALLY TRUE (verified against current sources):
- A fresh `sui client publish` is required, not an upgrade. The mainnet v1 package (0x7bf5274...) is missing njangi_compliance, njangi_cycle_escrow, whatsapp_integration; Sui upgrades cannot ADD modules. CONFIRMED: move/Published.toml:5-9 (mainnet v1) vs the 11 modules in move/sources/.
- The upgrade-cap pin sequencing is real and load-bearing. njangi_compliance.move:261-267 validates an UpgradeCap via two arms: arm1 `package::upgrade_package(cap)==@njangi` (works ONLY on a never-upgraded lineage) and arm2 `object::id(cap)==@njangi_upgrade_cap` (the pinned object id). A fresh publish + bootstrap succeeds via arm1, but after the first upgrade ONLY arm2 works — so the stale pin (move/config/mainnet.toml:34, 0xd8ca29...) MUST be replaced with the new cap's object id before any upgrade.
- Deployer 0xdde1086... holds 1.46 SUI on mainnet (verified live via sui client balance). Enough for the publish itself but thin for 11 modules + 3 bootstrap txns + buffer; top up to 5 SUI.

CORRECTIONS TO THE cost-risk REPORT (it reviewed stale findings, not the current code):
- "Escrow has no refund/cancel/timeout" — FALSE for current code. njangi_cycle_escrow.move:688 cancel_unfinalized_escrow, :705 cancel_unfinalized_escrow_for_recovery, :753 refund_expired_claim, with refunded-flag guards at :447/:573. The task framing confirms the 2026-06-12 package shipped "escrow refund paths."
- "Legacy payout over-pays by one contribution" — FIXED. njangi_payments.move:395-416 now uses contributing_members (member_count-1), with an explicit fix comment.
- "KYC gate is localStorage-only / bypassable" — PARTLY STALE. The escrow rail is now authoritatively gated on-chain: njangi_cycle_escrow.move:311-512 pins the exact ComplianceConfig object id, pins expected_issuer, and enforces revocation/expiry. Residual risk is only that the legacy contribute path still exists alongside the gated escrow path.

THE REAL BLOCKERS that make this a NO-GO are governance and launch-readiness, not contract fund-logic. See hardestBlockers.

## Hardest blockers

- NO PROFESSIONAL THIRD-PARTY AUDIT on contracts that will hold real funds. Posture is internal multi-agent adversarial review + 120 Move tests only (docs/gtm-readiness-review-2026-06-12.md:1-7). The fund-logic criticals are fixed, but escrow/compliance is brand-new code never seen by an external auditor. For a CEMAC pilot with real money this is the single largest risk — gate go-live on either a paid audit OR a hard-capped allowlist soft-launch.
- ATTESTORCAP + UPGRADECAP CUSTODY + the load-bearing pin sequencing. Bootstrap mints the AttestorCap to tx_context::sender (the hot deployer 0xdde1086...); the UpgradeCap is also on that hot key. Both are master keys (AttestorCap = forge any KYC pass; UpgradeCap = rewrite the contracts). They must move to a multisig. CRITICAL ORDERING: the new UpgradeCap object id must be pinned into move/config/mainnet.toml BEFORE any upgrade — fresh publish + bootstrap work via arm1, but the stale 0xd8ca29... pin will brick all UpgradeCap-gated bootstrap/recovery (E_FOREIGN_UPGRADE_CAP) the instant the lineage is upgraded (njangi_compliance.move:261-267).
- LAUNCH-READINESS GATES OUTSIDE THE CONTRACTS are unmet: (a) no Terms-of-Service / risk-disclosure acceptance gate before first contribution; (b) money-in unusable in launch geography — flows hardcode Coinbase+country=US, RampPicker is dead code, CEMAC users hit UNSUPPORTED_REGION; (c) ramp webhook integrity bugs (Transak fails-open on unset secret; Coinbase verifies re-serialized body not raw bytes); (d) git history still contains real PII (OAuth subs, zkLogin salts, recovery-code hashes) per the GTM review. None of these block the PUBLISH transaction, but all block a real-user mainnet launch.

## Decisions you must make first

- AUDIT: Pay for a third-party Move audit before go-live, OR accept internal-review-only and constrain blast radius with a hard-capped allowlist soft-launch? This is the gating decision for everything else.
- SOFT-LAUNCH SHAPE: Allowlist + per-circle member cap + per-circle fund cap + pilot duration, vs hard public launch? Recommend allowlisted, low-cap CEMAC pilot regardless of the audit decision.
- KEY CUSTODY: Which multisig holds the UpgradeCap and which holds the AttestorCap (same or separated)? Define the multisig policy (Sui native multisig, signer set, threshold) before publishing — ideally publish FROM it.
- MAINNET USDC: Native Circle USDC vs wormhole-wrapped legacy? Code silently defaults to wormhole-legacy if NEXT_PUBLIC_MAINNET_USDC is unset (src/services/network-config.ts:117). Pin the intended type explicitly.
- COMPLIANCE GATE AT LAUNCH: Enable on-chain attestation gating (requires_attestation + NEXT_PUBLIC_COMPLIANCE_GATE_ENABLED=true + issuer pin) at launch, or ship advisory-only? If enabled, the AttestorCap holder/issuer must be operational day one.
- OAUTH / ENOKI: Is ENOKI_API_KEY_MAINNET generated and ready (server-only), and are mainnet Google/Facebook/Apple OAuth client ids configured for the production domain?
- CETUS / YIELD: Confirm mainnet Cetus addresses (move/config/mainnet.toml:35-42) are correct for swap routing; confirm yield/Ember is deferred (no yield module in current sources — leave NEXT_PUBLIC_MAINNET_EMBER_* unset).
- OLD MAINNET STATE: Confirm the stale v1 package (0x7bf5274...) has zero live circles, so the fresh publish is a clean cutover with no migration/bridge needed.

## Sequencing vs the GTM checklist

Sequence relative to the GTM checklist: mainnet PUBLISH is a small, reversible-by-routing step that can technically happen any time — but USER-FACING LAUNCH must follow the readiness gates, not precede them. Recommended order: (1) Human decisions locked (audit yes/no, caps, custody) — week 0. (2) Counsel review of ToS/Privacy/Risk drafts + acceptance-gate implementation, and git-history scrub + secret rotation completed — these are PRE-publish because they touch live OAuth/PII the moment real users arrive. (3) Ramp webhook integrity fixes + at least one working CEMAC on-ramp (or an explicit crypto-in-only decision) — pre-launch, can overlap with publish. (4) Multisig provisioned. (5) PUBLISH + bootstrap + cap-transfer + env cutover (the runbook) — this is the mechanical step; do it once decisions 1-4 are settled, behind the allowlist so no real users are routed yet. (6) Walrus renewal cron verified live + DB migrated. (7) Stripe approval and Meta WhatsApp template approval are NOT blockers for the contract publish — Stripe gates the SaaS coordination subscription (revenue, no fund-flow fees per the Stripe plan) and Meta templates gate business-initiated WhatsApp nudges; both can land as fast-follows after a capped pilot proves the on-chain rails. (8) External audit (if chosen) gates the move from allowlisted pilot to open public mainnet. Net: publish behind an allowlist after legal + PII + custody are done; open the gates only after audit/pilot validation; treat Stripe + Meta as parallel revenue/notification tracks that do not block the publish itself.

## Runbook (do NOT start until the decisions above are locked)

1. 0. PRE-FLIGHT (do not publish yet). Confirm human decisions are made (see humanDecisions): audit yes/no, soft-launch caps, who holds UpgradeCap+AttestorCap, mainnet USDC type, compliance-gate on/off at launch. Top up deployer 0xdde1086... to ~5 SUI on mainnet (currently 1.46 — verified live).
2. 1. Freeze testnet publishing for the duration of the cutover so the two lineages do not diverge further. Confirm clean tree on the contracts you intend to ship (git status on move/sources/).
3. 2. Switch the Move manifest to mainnet: `bash move/scripts/switch-network.sh mainnet`, then `npm run validate:move-network` (byte-equal guard vs move/config/mainnet.toml).
4. 3. Dry build on mainnet config: `cd move && ./build_and_test.sh --build-only --network=mainnet` (or `--network=mainnet --build-only`). Must compile clean — no VM verification errors, no Sui version mismatch.
5. 4. Point the Sui CLI at mainnet from the multisig-or-deployer wallet you decided owns the lineage: `sui client switch --env mainnet` and confirm `sui client active-address` is the intended publisher. NOTE: whoever runs the publish receives the new UpgradeCap and (in step 6) the AttestorCap — publish from the multisig if policy requires, otherwise plan an immediate post-bootstrap transfer (step 8).
6. 5. PUBLISH (real SUI spent here): `cd move && ./build_and_test.sh --network=mainnet`. This runs ensure_network_consistency, publishes, writes published-at/original-id/upgrade-capability into move/Published.toml [published.mainnet], patches NEXT_PUBLIC_MAINNET_*_PACKAGE_ID in .env.local, and auto-syncs src/lib/circle-chain.ts PACKAGE_LINEAGE_BY_NETWORK.mainnet via update_circle_chain_lineage() (perl regex sourced from Published.toml). Record the NEW package id and the NEW UpgradeCap object id from the publish output.
7. 6. *** CRITICAL UPGRADE-CAP PIN STEP — do this BEFORE any future upgrade *** Open move/config/mainnet.toml and replace njangi_upgrade_cap = 0xd8ca29501b1f1eaee88d37d509e9c80cd5ae45d29acc198137c525aa36e7117c (line 34) with the NEW UpgradeCap object id from step 5. Also update the explanatory comment (lines 26-33) to reference the new publish tx. The fresh publish + this bootstrap succeed via arm1 (njangi_compliance.move:262 runtime-id match) even with the stale pin — but arm2 (the pinned object id, njangi_compliance.move:264) becomes the SOLE validator after the first upgrade. Pin it now so any later upgrade or recovery call does not abort with E_FOREIGN_UPGRADE_CAP (306).
8. 7. BOOTSTRAP the registries against the new package, on mainnet: `NJANGI_BOOTSTRAP_NETWORK=mainnet node scripts/bootstrap-package.mjs <NEW_PACKAGE_ID>` (build_and_test.sh prompts to run this automatically post-publish — answer y). This calls njangi_compliance::create_config(upgrade_cap) (mints/records the AttestorCap + ComplianceConfig), njangi_price_validator::init_registry, whatsapp_integration::init_registry, and idempotently writes NEXT_PUBLIC_MAINNET_NJANGI_ATTESTOR_CAP_ID, NEXT_PUBLIC_MAINNET_NJANGI_ASSET_REGISTRY_ID, NEXT_PUBLIC_MAINNET_WHATSAPP_REGISTRY_ID, NEXT_PUBLIC_NJANGI_ATTESTATION_ISSUER into .env.local. Capture the AttestorCap object id from the bootstrap output.
9. 8. TRANSFER MASTER KEYS to the multisig: call njangi_compliance::transfer_attestor_cap(cap, multisig_addr) (the only path — cap is key-only, emits AttestorCapTransferred). Then transfer the UpgradeCap object to the same/another multisig. After moving the AttestorCap, call njangi_compliance::set_expected_issuer to the multisig issuer address so the on-chain gate accepts the new issuer, and update NEXT_PUBLIC_NJANGI_ATTESTATION_ISSUER to match. (Revocation is cap-holder-authorized, not issuer-bound, per njangi_compliance.move:30-38, so multisig custody does NOT brick revocation in current code.)
10. 9. SET VERCEL PRODUCTION ENV: NEXT_PUBLIC_SUI_NETWORK=mainnet; NEXT_PUBLIC_MAINNET_PACKAGE_ID, NEXT_PUBLIC_MAINNET_WHATSAPP_PACKAGE_ID, NEXT_PUBLIC_MAINNET_WHATSAPP_REGISTRY_ID, NEXT_PUBLIC_MAINNET_NJANGI_ATTESTOR_CAP_ID, NEXT_PUBLIC_MAINNET_NJANGI_ASSET_REGISTRY_ID (from steps 5/7); NEXT_PUBLIC_MAINNET_USDC (decide native Circle USDC vs wormhole-legacy — code defaults to wormhole if unset, src/services/network-config.ts:117); NEXT_PUBLIC_MAINNET_CETUS_* (from move/config/mainnet.toml:35-42); ENOKI_API_KEY_MAINNET (server-only, separate from testnet, NO NEXT_PUBLIC_ prefix); WALRUS_PII_MASTER_KEY/WALRUS_LOOKUP_SALT/WALRUS_PUBLISHER_URL/WALRUS_AGGREGATOR_URL; COMPLIANCE_* / INTERNAL_NOTIFY_SECRET / CRON_SECRET; production WHATSAPP_* (mainnet Meta account). Ensure no server secret carries NEXT_PUBLIC_.
11. 10. DATABASE: run `npm run migrate:postgres` against the mainnet Neon DB (idempotent; creates the 7 app tables incl. whatsapp_phone_index.walrus_end_epoch + walrus_renewal_audit). DATABASE_URL must be set or the compliance queue silently falls back to in-memory.
12. 11. VALIDATE ENV: `npm run validate:env` with the mainnet env loaded — must confirm all NEXT_PUBLIC_MAINNET_* ids + attestor cap + asset registry + ENOKI_API_KEY_MAINNET are populated (scripts/validate-env.mjs:117-159).
13. 12. SMOKE: there is no smoke:mainnet script — run the testnet smoke against the mainnet URL: `SMOKE_BASE_URL=<prod-url> SMOKE_NETWORK=mainnet node scripts/smoke-testnet.mjs`. Expect all PASS. Then manual UX walk-through (/admin/compliance queue renders; /circle/<id>/contribute shows the WhatsApp-link prompt).
14. 13. VERIFY CRONS on Vercel: /api/cron/cycle-finalized, /api/cron/whatsapp-circle-events, /api/cron/walrus-renewal (daily) are scheduled and authenticate via CRON_SECRET. The walrus-renewal cron MUST be live before any PII is encrypted on mainnet (blobs expire ~5 epochs while on-chain anchors persist).
15. 14. COMMIT the cutover artifacts that build_and_test.sh modified: move/Published.toml [published.mainnet], move/config/mainnet.toml (new pin), src/lib/circle-chain.ts (mainnet lineage). Do NOT commit .env.local (holds live Neon creds + secrets). `npm run preflight` once more before pushing.
16. 15. ROLLBACK PLAN: if smoke/UX fails, flip Vercel NEXT_PUBLIC_SUI_NETWORK back to testnet and redeploy — the published mainnet package stays dormant (no users routed to it). The package itself cannot be un-published; rollback is purely an env/routing flip, which is why the soft-launch allowlist (humanDecisions) matters.
